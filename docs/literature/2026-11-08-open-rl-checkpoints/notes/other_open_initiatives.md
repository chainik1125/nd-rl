# Non-AllenAI open-science and open-checkpoint LLM families (≥ 7B) with RL-stage checkpoints

Scope: inventory of non-AllenAI model families at ≥ 7B total parameters where online RL (RLVR, GRPO, PPO, RLOO, async GRPO, etc.) is the last training stage of a released checkpoint, and where the checkpoint RL started from (and ideally intermediate RL checkpoints) is public. Status as of 2026-11-08.

How things were verified. Every repo id, branch/tag list, parameter count, licence field and gating flag marked **[HF-verified]** was read directly from the Hugging Face API with `curl` on 2026-11-08 (`/api/models/{repo}`, `/api/models/{repo}/refs`, `/api/models/{repo}/tree/{rev}`, `/api/models?author={org}`, and `/{repo}/raw/main/README.md`). Parameter counts are the `safetensors.total` field of the API (BF16 tensors), so they include embeddings and MTP heads and can differ from the marketing name. **[card]** = stated in the model card on HF (read raw, not paraphrased by a third party). **[paper/blog]** = only stated in a paper or blog. **[secondary]** = only in third-party coverage. Unauthenticated access was used throughout; no gated repo terms were accepted, so gated repos' refs are reported as not visible.

Note on the LLM360 org: `huggingface.co/LLM360/*` now 307-redirects to the **`IFM`** org (MBZUAI Institute of Foundation Models); `api/models?author=LLM360` returns 0 repos and `author=IFM` returns 121 **[HF-verified]**. Repo ids below use `IFM/…`; the old `LLM360/…` ids still redirect.

## Which families qualify, and the exact repos and sizes

### Takeaway
Two non-AllenAI releases reach grade A, i.e. RL start + RL model + intermediate RL checkpoints.
- **NVIDIA Nemotron-Cascade-8B** is the strongest. Its pipeline is Qwen3-8B-Base → SFT → RLHF → IF-RL → Math-RL → Code-RL → SWE-RL, and it releases the SFT start and the four stage-boundary RL checkpoints as subfolders of one repo.
- **Prime Intellect INTELLECT-MATH 7B** is the other, a thinner case: SFT → RL step 47 → RL step 255, as separate repos.

The most interesting new find is **IFM (ex-LLM360) K2-Horizon**, released Sept 2026 at 9B dense and 375B-A23B MoE.
- Per-domain RL "expert" checkpoints are exposed as revision tags, next to the exact midtraining tag they started from.
- Its released `main` is not RL-final: for this family RL comes before SFT, and the 7B also gets an FTPO preference stage.

Grade-B pairs (exact or card-named start + RL model) are now fairly common:
- **Swiss AI Apertus v1.5** has `-SFT` and `-RL` repos, but they are gated, and RL is followed by DPO/SDPO.
- **Swallow** has Qwen3-Swallow and GPT-OSS-Swallow `-SFT`/`-RL` pairs at 8B–120B.
- **LumiOpen Poro 2**: 8B math SFT → RL preview.
- **Xiaomi MiMo-7B**: SFT → RL, and Base → RL-Zero.
- **Prime Intellect**: INTELLECT-3 → 3.1, and QwQ-32B → INTELLECT-2.
- **OpenThoughts-Agent**: two 8B SFT → RL pairs.
- **AMD Instella-MoE 16B-A3B**: DPO → IF-RL + on-policy distillation.
- **IFM K2-Think-V2**: K2-V2-Instruct → RLVR.
- **NVIDIA AceReason**: DeepSeek-R1-Distill → RL.

NVIDIA's flagship open-data lines (Nemotron 3 Nano/Super/Ultra, Llama-Nemotron) release only Base and final, with no SFT or RL-stage checkpoints. Granite 4.x, Falcon-H1R, Trinity, ZAYA1 and Moxin are the same.

- India: `sarvamai` has `sarvam-m`, `sarvam-30b`, `sarvam-105b` (2026-03) and no stage checkpoints **[HF-verified listing]**.

### Inferences
- Among non-AllenAI groups, "RL start + RL model" pairs are now common (Swallow, Poro, MiMo, OpenThoughts, Prime Intellect, Apertus, Instella, Cascade). True intermediate-RL trajectories, with many steps within one RL run, remain rare. Nemotron-Cascade gives stage-boundary checkpoints and K2-Horizon gives per-expert endpoints; neither exposes `step_XXXX` revisions inside an RL run the way Olmo 3.1 does. The only within-run intermediate found is INTELLECT-MATH's step 47 of 255.
- K2-Horizon's RL→SFT ordering makes its released `main` unsuitable as "the RL model", but the `mid_4_10000 → rl_math → rl_code1 → rl_code2` chain is a clean three-step sequential-RL trajectory with exact starts, at ~9B and (via the five-expert fan-out) at 375B-A23B.

### Gaps
- Apertus v1.5 refs, files and card are gated (`gated: auto`); I did not accept the terms, so I could not see whether the repos carry intermediate RL branches, or compare tokenizers.
- No K2-Horizon technical report was available ("Technical report | Not yet available | In Progress | End of September 2026" on the card, last updated 2026-10-01), and the `ifm.ai/blog/k2/` page returned 403 to my fetcher.
- I did not enumerate every NVIDIA repo (the org is very large); I searched it with 23 keyword queries (Nemotron, AceReason, OpenReasoning, OpenMath, OpenCode, Cascade, ProRL, BroRL, SFT, RL, Intermediate, ckpt, checkpoint, pre-RL, Stage, Qwen3, Qwen2.5, DeepSeek, Llama-3, Instruct, Reasoning, Math, Thinking), so a stage-checkpoint repo with an unusual name could be missing.

## Intermediate RL checkpoints: how many, at which steps, and how exposed

### Takeaway
No non-AllenAI family found exposes within-run RL step checkpoints as HF revisions. The only within-run intermediate found is Prime Intellect's 7B INTELLECT-MATH (separate `-step-47` repo between `-SFT` and the step-255 final). Nemotron-Cascade-8B gives five stage-boundary checkpoints (SFT plus four RL stages) as subfolders. K2-Horizon gives per-expert RL endpoints and the merged RL checkpoint as tags. Apertus v1.5 says intermediate checkpoints are public, but its gated repos could not be inspected. Everything else ships one RL checkpoint, sometimes an early-stopped step.

### Cited Findings
- **Nemotron-Cascade-8B**: subfolders `Nemotron-Cascade-8B-SFT/`, `-RLHF/`, `-IFRL/`, `-MathRL/`, `-CodeRL/` in `nvidia/Nemotron-Cascade-8B-Intermediate-ckpts`; final (post-SWE-RL) in `nvidia/Nemotron-Cascade-8B` **[HF-verified]**. Card benchmark rows show large per-stage movement, e.g. IFEval (strict prompt) 70.8 (SFT) → 50.1 (RLHF) → 90.4 (IFRL) → 92.1 (MathRL) → 90.7 (CodeRL) → 90.2 (final); AIME 2025 72.8 → 75.0 → 75.2 → 81.9 → 80.5 → 80.1 **[card]** — [Intermediate ckpts](https://huggingface.co/nvidia/Nemotron-Cascade-8B-Intermediate-ckpts). - **K2-Horizon-7B**: tags `rl_math` (2,399 steps), `rl_code1` (601), `rl_code2` (1,499), `rl_search` (59), `rl_tool-use` (39), `rl_merged`; "only the exported checkpoint is retained" for Search and Tool-use **[HF-verified tags + card]**. **K2-Horizon-375B-A23B**: tags `rl_knowledge_work`, `rl_if`, `rl_search`, `rl_tool-use`, `rl_reasoning`, `rl_merged` (step counts given as "-") **[HF-verified + card]**.

- Nemotron-Cascade-8B is the only non-AllenAI release found where one can run "start vs. each successive RL stage" on a single 8B lineage without merging confounds. ## RL setup: algorithm, rewards, domains, compute

### Takeaway
GRPO and its DAPO-style variants dominate (Cascade, Nemotron 3, Granite, Falcon-H1R, Instella, K2-Think-V2, INTELLECT, Poro via prime-rl, Swallow via slime); OpenThoughts-Agent uses RLOO-style advantages; Llama-Nemotron mixes GRPO, RLOO and online RPO. Domains run from math-only (Swallow, Poro, AceMath) to multi-environment agentic RL (Nemotron 3, INTELLECT-3, K2-Horizon, OpenThoughts-Agent).

### Cited Findings
- **Nemotron-Cascade**: "GRPO with strict on-policy updates: each batch of G rollouts gets a single gradient update", "we remove KL divergence term entirely", token-level loss, verl; RLHF uses a Bradley–Terry reward model initialised from Qwen2.5-72B-Instruct (released as `nvidia/Qwen2.5-CascadeRL-RM-72B`); "fast symbolic rule-based verification" for math; "slow execution-based verification" for code and SWE **[paper + HF collection]** — [arXiv 2512.13607](https://arxiv.org/html/2512.13607v2), [collection](https://huggingface.co/collections/nvidia/nemotron-cascade)
- **Nemotron 3 Nano**: "multi-environment reinforcement learning using synchronous GRPO … across math, code, science, instruction following, multi-step tool use, multi-turn conversations, and structured output environments", then RLHF with a generative reward model; NeMo RL + NeMo Gym. **Super/Ultra**: "asynchronous GRPO" over the same environment list; Ultra adds MOPD **[card]** — [Nano](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16), [Super](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-BF16), [Ultra](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B-BF16)
- **Llama-Nemotron**: Nano gets "two rounds of offline RPO"; Super gets RLOO IF-RL then iterative online RPO plus merging; Ultra gets GRPO reasoning RL ("72 nodes of 8xH100"; "the whole training takes approximately 140k H100 hours"), then RLOO IF-RL, then RLHF **[paper]** — [arXiv 2505.00949](https://arxiv.org/html/2505.00949). Super-49B-v1.5: "RPO for chat, RLVR for reasoning, and iterative DPO for Tool Calling … The final checkpoint was achieved after merging several RL and DPO checkpoints" **[card]**. Nano-8B-v1: "final model checkpoint is obtained after merging the final SFT and Online RPO checkpoints" **[card]**. The card's "Online RPO" conflicts with the paper's "two rounds of offline RPO with on-policy data" for LN-Nano; either way the final is a merge.
- **Instella-MoE**: Stage 1 "GRPO + DAPO + R3, 1,400 steps", 64 prompts × 8 responses, max response 16,384, rewards "produced by deterministic verifiers rather than a learned reward model" (IF constraints, partial credit); Stage 2 MOPD with per-token advantage "the teacher–student log-probability gap"; each run on 24 GPUs (8 learner, 16 SGLang rollout) using the Miles framework **[paper]** — [Instella report](https://arxiv.org/html/2609.00791v1)
- **K2-Think-V2**: GRPO-based RLVR without KL and entropy losses, asymmetric clipping with high clip 0.28 **[secondary]**; RL data "Guru (v1.5) … Math, Code, and Science subset of Guru-92k … specially filtered according to the capabilities of K2-V2": 102K math, 1.5K code, 5.1K science prompts (108.8K) **[HF dataset card]** — [IFM/guru-RL-v1.5](https://huggingface.co/datasets/IFM/guru-RL-v1.5)
- **K2-Horizon**: RL algorithm and reward definitions are not stated on the cards; per-expert domains are math, code, search agent, tool use (7B) and knowledge work, IF, search, tool use, reasoning (375B); 7B RL token budgets 29.1B (math), 6.2B + 12.3B (code), 8.4B (search), 1.4B (tool use) **[card]**.
- **Apertus v1.5**: "RL with verifiable rewards (RLVR)" "on about 350k math, code, instruction-following, multilingual, and vision prompts", "mixing thinking on and off"; code `github.com/swiss-ai/verl` and verl-recipe **[blog]**.
- **Swallow**: "RLVR was conducted using slime"; "maximum number of output tokens was set to 24,576"; data "Math subset of allenai/Dolci-Think-RL-7B"; algorithm not named **[card]**.
- **Poro 2**: "We use the Prime-RL framework for running GRPO-like verifiable reinforcement learning", KL penalty 0.01, math-verify rewards, dataset `Kwai-Klear/KlearReasoner-MathSub-30K` with English and Finnish environments **[blog]** — [AMD ROCm playbook](https://rocm.blogs.amd.com/artificial-intelligence/rl-training-playbook/README.html)
- **MiMo-7B**: "130K mathematics and code problems … verified by rule-based verifiers … only rule-based accuracy rewards", "test difficulty driven code reward" **[card]**.
- **OpenThoughts-Agent 8B RL**: rollouts in Daytona sandboxes rewarded by each task's test verifier; "RLOO-n advantage estimator, with no KL loss", PPO clipping; task set `OpenThoughts-Agent-RL-5K` **[card, via search snippet]**.
- **INTELLECT-3 / 3.1**: prime-rl (async-only) with verifiers-library environments on the Environments Hub; 512 H200s **[card + report summary]** — [INTELLECT-3](https://huggingface.co/PrimeIntellect/INTELLECT-3), [arXiv 2512.16144](https://arxiv.org/abs/2512.16144v1). **INTELLECT-2**: "GRPO over verifiable rewards", dataset `PrimeIntellect/INTELLECT-2-RL-Dataset` **[card]** — [INTELLECT-2](https://huggingface.co/PrimeIntellect/INTELLECT-2)
- **Granite 4.1**: "on-policy GRPO with DAPO loss", dynamic sampling off, 16 samples per prompt, batch 1,024, 8,192 context, SkyRL; prompts per stage ≈ 45,504 / 17,920 / 1,728 / 13,504 **[blog]** — [Granite 4.1 blog](https://huggingface.co/blog/ibm-granite/granite-4-1). **Granite 4.2**: GRPO on NeMo RL / NeMo Gym, then RLHF **[card]**.
- **Falcon-H1R-7B**: GRPO; "Rewards are given for correct reasoning chains" **[blog]**.
- **ZAYA1-8B**: four-phase RL cascade (reasoning warmup; "400-task RLVE-Gym curriculum"; math and code RL; behavioural RLHF/RLAIF) **[blog / press]** — [Zyphra blog](https://zyphra.com/post/zaya1-8b)
- **AceReason-Nemotron**: math-only then code-only RL; math RL data `nvidia/AceReason-Math` **[card]**.
- **MiMo-V2.6-Flash-RL**: "Fully asynchronous … GRPO on very large batches — 1,568 prompts × 16 rollouts per step", agentic grader rewards, then MOPD2 produces `-MOPD` **[card]** — [MiMo-V2.6-Flash-RL](https://huggingface.co/XiaomiMiMo/MiMo-V2.6-Flash-RL)

### Inferences
- If the goal is IF-specific reach, Nemotron-Cascade's IF-RL stage (IFEval 50.1 → 90.4 between adjacent released checkpoints) and Instella's IF-RL (start = DPO) are the most targeted IF-RL pairs; for math, Swallow, Poro, AceReason, MiMo and K2-Horizon `rl_math` are math-only RL.

## Parity: tokenizer and chat template between RL start and RL model

### Takeaway
I compared tokenizer and template files between each RL start and its RL model through the HF tree API (git blob oids). Where oids differed I diffed the files themselves. In every pair checked, `tokenizer.json` is identical, apart from the two external-start pairs (AceReason vs. R1-Distill, INTELLECT-2 vs. QwQ), which are noted below. Chat templates are identical for MiMo, Swallow, Poro, Instella, OpenThoughts-Agent and K2-Horizon. They differ in small, documentable ways for K2-Think-V2 and INTELLECT-3.1. They differ materially for **Nemotron-Cascade's SFT checkpoint versus its RL stages**: the RL-stage templates auto-append ` /think` or ` /no_think` and add a default system prompt, while the SFT template does neither. Prompts therefore have to be rendered by hand to match.

### Cited Findings
All rows below are **[HF-verified]**: file oids come from `/api/models/{repo}/tree/{rev}[/{subfolder}]`, and file contents from `/{repo}/raw/{rev}/…`, read on 2026-11-08.
- **Nemotron-Cascade-8B**: `tokenizer.json` and `special_tokens_map.json` are the same from `…-SFT/` through to `Nemotron-Cascade-8B`; `tokenizer_config.json` differs only in the `chat_template` key. The SFT template is 4,116 chars and the RLHF/CodeRL templates 4,611; the final is 4,621. The RL-stage templates add a default system prompt ("You are a helpful and harmless assistant.") and append ` /think` or ` /no_think` to the last user turn depending on `enable_thinking`. The SFT template does neither, and instead emits an empty `<think>\n\n</think>` when `enable_thinking` is false. RLHF and final differ in one line: the final template appends ` /no_think` to non-final user turns. `generation_config.json` differs in bos/eos/pad ids and `max_new_tokens`. This contradicts the card's "All intermediate checkpoints use the same chat template as Nemotron-Cascade-8B" for the SFT subfolder — [SFT tokenizer_config](https://huggingface.co/nvidia/Nemotron-Cascade-8B-Intermediate-ckpts/blob/main/Nemotron-Cascade-8B-SFT/tokenizer_config.json)
- **K2-Horizon-7B** `mid_4_10000` vs `rl_math` and `rl_merged`: `tokenizer.json`, `chat_template.jinja` and `generation_config.json` are the same. `tokenizer_config.json` differs only because the RL tags also embed the template (51,034 chars, byte-equal to the `mid_4_10000` `chat_template.jinja`); `special_tokens_map.json` exists only in the RL tags. **375B-A23B** `mid_4_6000` vs `rl_reasoning`: tokenizer, tokenizer_config and template are the same; `special_tokens_map.json` differs.
- **K2-V2-Instruct → K2-Think-V2**: `tokenizer.json` is the same; `tokenizer_config.json` differs only in `pad_token`. `chat_template.jinja` differs in two lines: `reasoning_effort | default('medium')` becomes `default('high')`, and one assistant-prefix line changes from `<think_fast>` to `<think>`.
- **MiMo-7B** SFT→RL and Base→RL-Zero: all tokenizer and generation files are the same.
- **Qwen3-Swallow-8B** and **GPT-OSS-Swallow-20B** SFT→RL: `tokenizer.json`, `tokenizer_config.json`, `chat_template.jinja`, `special_tokens_map.json` and `generation_config.json` are all the same.
- **Poro 2 8B Long Math** SFT→RL: all tokenizer and template files are the same; only the RL repo has a `generation_config.json`.
- **Instella-MoE** DPO→Think: all tokenizer and generation files are the same.
- **OpenThoughts-Agent**: in cold-start SFT→RL, `tokenizer.json` and `chat_template.jinja` are the same and `tokenizer_config.json` differs only in `padding_side`. In v1-SFT→v1 the template moved from `chat_template.jinja` into `tokenizer_config.json` but is byte-identical (4,168 chars).
- **INTELLECT-3 → 3.1**: `tokenizer.json` is the same; `tokenizer_config.json` differs only in `pad_token`. `chat_template.jinja` differs in one line, the default system prompt identity: "You are INTELLECT-3, …" becomes "You are INTELLECT-4, …".
- **INTELLECT-MATH-SFT → INTELLECT-MATH**: `tokenizer_config.json` and `special_tokens_map.json` are the same; the SFT repo ships `vocab.json`/`merges.txt` and no `tokenizer.json`; `generation_config.json` differs.
- External-start pairs, **DeepSeek-R1-Distill-Qwen-7B → AceReason-Nemotron-7B** and **QwQ-32B → INTELLECT-2**: `tokenizer.json` and `tokenizer_config.json` oids differ. On parsing both files: the vocab is identical (151,643 entries each), the added tokens are identical (22 and 26 respectively), and the `chat_template` is identical, but the `merges` lists are not equal as stored. This may only be a serialization-format change; I did not check. For AceReason the `tokenizer_config.json` also differs in `bos_token`, `eos_token`, `pad_token`, `added_tokens_decoder`, `extra_special_tokens` and `use_default_system_prompt`; for INTELLECT-2 only in `extra_special_tokens`.

### Inferences
- For Nemotron-Cascade, a fair start-vs-RL comparison needs one fixed rendering. One option is the final template with an explicit ` /think` and no default system prompt, applied to both the `…-SFT/` and RL checkpoints. Otherwise the SFT model sees prompts without the ` /think` tag it was trained to respond to. This is the kind of template mismatch that can masquerade as "reach".
- For K2-Think-V2 vs K2-V2-Instruct, pass `reasoning_effort="high"` explicitly to both. The only other template change (`<think_fast>` → `<think>`) sits on one assistant-prefix line, which I did not trace to a specific effort level.
- AceReason and INTELLECT-2 tokenizers are vocabulary-identical to their external starts, but differing `eos_token` or `pad_token` settings (AceReason) can change stopping behaviour in vLLM unless pinned.

### Gaps
- Apertus v1.5 parity could not be checked (gated).
- I did not check parity for the Qwen3-Swallow 30B-A3B/32B pairs, GPT-OSS-Swallow 120B, Cascade's IFRL and MathRL subfolders (only SFT, RLHF, CodeRL and final), or the K2-Horizon `rl_code*`, `rl_search` and `rl_tool-use` tags.
