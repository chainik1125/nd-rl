# Cross-fitted stopping follow-up: feasibility and reason to defer

Root accepted the reviewer's recommendation to defer. This note records interface inspection only: no fold fit, training, fresh generation or additional current-TEST inference ran. Current MAIN/historical registries and their execution priorities remain unchanged.

Five frozen-head fits are technically straightforward on CPU. `selectors/frozen_head_features_v1/train_features.npz` already contains 12,800 candidate representations from 1,600 TRAIN theorems, 384 FP32 dimensions each, with canonical IDs and families. The original trunk is unchanged. Assign each theorem skeleton to one of five prospectively seeded, family-balanced folds and keep all eight candidates together. Fit the same 385-parameter FP64 head on four folds and score the fifth. Join full TRAIN labels before masking: `frozen_head_common.aligned_labels` intentionally requires exact full-cache key equality. Reusing `fit_frozen_head.fit` from a separate wrapper avoids its CLI's subsequent DEV evaluation. Five fits need no GPU; the existing full-data CPU solve took about 1.5 seconds, so tens of CPU seconds is a reasonable conservative estimate, not a measured five-fold runtime.

The scientific complication is score transfer. Stopping would train on five different 80%-data heads but deploy the existing 100%-data head. Out-of-fold confidence need not have the deployed head's calibration. Fresh calibration data could address this, but would require a symmetric, prospectively fixed calibration opportunity for adaptive and constant/count-only controls. The existing current TEST must not supply that calibration. This complication makes the otherwise cheap CPU fit a nontrivial new study.

For a future 400–800-theorem pool, a separate generator wrapper should preserve the frozen 50/50 forward/ORE2 knobs but expose new independent RNG seeds, refuse existing output paths and enforce an explicit global skeleton exclusion set. Exclude all 2,320 current corpus skeletons, all pilot skeletons, and known pretraining/EI skeletons derived from the audited exposure cache, as well as canonical atom/premise equivalents of public benchmarks. Keep calibration and fresh TEST skeletons disjoint. Hash and snapshot exclusions, seed assignments and source before candidate generation; reject only structural/exposure/certificate failures, never generator outcomes. Reference certificates remain private and outside scorer/stopping inputs. Existing `main_data.py` has hardcoded seeds and canonical exclusions, so it is a source interface to reuse, not a ready fresh-pool command.

Observed MAIN 400×8 collection required 920.28 seconds after model loading, including Lean/environment overhead and diagnostic replay. The registered frozen-head MAIN 400 inference child took 17.21 seconds. Linear estimates therefore suggest roughly 16 GPU-assigned minutes for 400 theorems or 32 for 800, plus launch/load overhead; under foreign co-location these are scheduling estimates, not isolated latency promises. Fresh 400-theorem calibration would add roughly another 16 minutes. Unneeded likelihood replay could be omitted in a separately audited collector, but no such faster implementation is assumed here.

Minimum new work would be a versioned fold/label audit, CPU cross-fit wrapper, TRAIN-only threshold/control fitter covering all legal counts 1–8, score-transfer/calibration protocol, explicit fresh-skeleton generator, immutable new method/public-pool registries, guarded evaluator and paired statistics. Independently reproduce fold exclusions, out-of-fold logits, optimizer diagnostics, identical original generator tensors, inference score equivalence and threshold-fitting symmetry. Report both calibration-transfer risk and post-hoc motivation. None of that justifies changing this sprint's frozen claims or delaying its historical evaluations.
